# 项目说明文档（项目汇报配套）

> 项目名称：基于大模型微调的医疗专家
> 技术路线：Qwen2.5-7B-Instruct + PEFT/LoRA + 4bit 量化微调（QLoRA）+ 云端全量训练 + Gradio 部署
> 本文档与 PPT《基于大模型微调的医疗专家》一一对应，可直接作为项目汇报讲稿素材。
> 2026-11-07 修订：补充云端全量训练实测结果与回迁验证，统一可训练参数口径。

---

## 一、项目背景（对应 PPT 第 2~4 页）

### 1.1 行业痛点

- **医疗资源分布不均**：基层医疗机构误诊率明显高于三甲医院（约 40% vs 5%），优质诊断能力稀缺；
- **跨学科复杂病例分析效率低**：涉及多科室知识的综合判断耗时费力；
- **医生知识更新滞后**：医学文献指数级增长，人工跟进困难。

### 1.2 技术机遇

- 大语言模型具备强大的**知识整合与推理能力**，适合医学问答辅助场景；
- 医疗数据数字化加速（电子病历、公开问答数据集），为领域微调提供燃料。

### 1.3 通用模型的医疗瓶颈

直接使用通用大模型做医疗问诊存在三大问题：

| 瓶颈 | 表现 | 本项目对策 |
|---|---|---|
| 专业知识不足 | 医学术语使用随意、诊断依据薄弱 | 2 万条专业医疗 CoT 数据微调注入领域能力 |
| 缺乏推理过程 | 直接给结论，无法体现医学思辨 | 训练数据含思维链，模型学会"先推理后解答" |
| 回答风格不稳 | 口语化、结构散乱 | 统一 system prompt + 固定回答结构 |

### 1.4 项目目标

> 微调是增强大模型原生能力的最佳方法：可优化语气风格、增强推理能力、进行领域知识灌注。
> 本项目以**蒸馏得到的中文医疗思维链数据集**（2 万条问答对，含专家级推理过程），
> 对 Qwen2.5-7B-Instruct 进行专项微调，得到一个能输出结构化医学推理的**医疗领域专家模型**，
> 并通过 Web 界面提供本地化的问诊演示服务。

```
普通大模型(LLM)  +  医疗数据(2万条CoT)  ──LoRA微调──▶  医疗专家大模型(Specialist LLM)
```

## 二、技术栈选择（对应 PPT 第 5~6 页）

### 2.1 基座模型：Qwen2.5-7B-Instruct

- 通义千问开源 7B 指令模型，中文能力国内领先，原厂 ChatML 对话模板成熟；
- 7B 规模在"能力与资源"之间平衡最佳，配合量化可在家用显卡上完成微调。

### 2.2 微调方案：PEFT + LoRA（对比说明）

| 方案 | 显存需求(7B) | 说明 |
|---|---|---|
| 全参数微调 | ~80GB (A100×2) | 效果上限高但不可行 |
| **PEFT + LoRA（本项目）** | **~10GB** | 冻结基座，仅训练低秩增量矩阵（40.37M 参数，约 0.5%） |
| Unsloth | ~8GB | 第三方加速框架，PPT 中提及；本项目改用 HuggingFace 官方栈（Transformers+PEFT），兼容性与稳定性更适合 Windows 本地环境，且两者 LoRA 产物格式互通 |

LoRA 原理一句话：冻结预训练权重 W，训练两个低秩矩阵 A(d×r)、B(r×d)，
前向计算变为 `h = Wx + (α/r)·BAx`；r=16、挂载 7 类线性层 × 28 层时，
可训练参数 **40,370,176 ≈ 40.37M**（占 7.62B 基座约 0.5%），效果接近全参微调。

> 口径提示：部分训练日志按 4bit 量化后 PEFT 统计的分母显示「0.92%」，与按原始基座核算的 0.53% 不同。对外统一讲「40.37M 可训练参数」即可，避免分母争议。

### 2.3 显存优化三件套（QLoRA）

1. **BitsAndBytes 4bit NF4 量化**：基座压至约 5.6GB 显存；
2. **梯度检查点（Gradient Checkpointing）**：以重算换显存，峰值再降约 40%；
3. **paged_adamw_8bit 分页优化器**：优化器状态 8bit 化，防显存峰值溢出。

### 2.4 完整技术栈

| 层次 | 组件 |
|---|---|
| 基座模型 | Qwen/Qwen2.5-7B-Instruct |
| 本地微调框架 | Transformers (Trainer) + PEFT (LoRA) + Accelerate |
| 云端微调框架 | ModelScope Notebook GPU + ms-swift 4.5.3（`swift sft`，BF16 + Flash Attention 2） |
| 量化 | BitsAndBytes（4bit NF4 + 双重量化） |
| 数据 | medical_cot_zh.jsonl（20171 条，Question/Complex_CoT/Response） |
| 推理 | Transformers generate + TextIteratorStreamer 流式输出 |
| 界面 | Gradio（Blocks 布局，强制免责声明 + 多轮对话） |

## 三、实现方式（对应"实现方式"章节）

### 3.1 数据工程

- **数据规模**：20171 条中文医疗问答，覆盖中西医各科室场景；
- **字段结构**：`Question`（患者提问）、`Complex_CoT`（专家思维链）、`Response`（专业回答）；
- **预处理流水线**（`data/preprocess.py`，已实测）：
  - 清洗：剔除缺失字段与超长样本（>1600 字符），保留 **20141 条**；
  - 格式化：三字段拼接为 ChatML 多轮对话，assistant 回复固定为
    `【医学推理】思维链 \n\n 【专业解答】结论` 的 CoT 外显结构；
  - 划分：随机打乱（seed=42）后按 95%/5% 划分 → **训练集 19134 条 / 验证集 1007 条**；
  - 托管：上传 ModelScope 私有数据集 `Huahai123654/medical-cot-zh`（53.2MB / 2.8MB）供云端训练。

### 3.2 本地训练工程（`train/train_lora.py`）

五个关键技术点（汇报讲解重点）：

1. **QLoRA 4bit 量化加载**：`load_in_4bit=True + nf4 + double_quant`；
2. **LoRA 配置**：`r=16, alpha=32, dropout=0.05`，挂载 Qwen 全部 7 类线性层
   （q/k/v/o/gate/up/down_proj），可训练参数 40.37M（约 0.5%）；
3. **Loss 屏蔽（关键正确性设计）**：利用 ChatML 前缀对比法，将 user/system
   部分 label 置 -100，**只对 assistant 回答计算交叉熵**——模型专注学"怎么答"
   而非"怎么问"（该逻辑已通过单元验证：仅 assistant 段携带监督信号）；
4. **动态 Padding Collator**：batch 内补齐至 8 的倍数，兼顾效率与 GPU 对齐；
5. **训练稳定性**：cosine 调度 + 3% 预热 + 梯度裁剪 0.3 + 早停（patience=3），
   验证集 loss 挑选最优 checkpoint。

超参摘要：1 epoch / lr 2e-4 / batch 2×accum 8=16 / max_length 1536（≥12GB 显存默认值）；
本机实测（RTX 4060 Laptop / 8GB）采用 batch 1×accum 16 / max_length ≤1024，
并额外启用 embed_tokens 与 lm_head 的 CPU offload（再省约 2GB 显存），
快速验证训练（200 条×1 epoch）train_loss=1.995，全流程无 OOM。

> **口径提示**：以上 loss mask / 动态 Padding / 早停 / CPU offload 均为**本地 200 条验证链路**的实现；云端全量训练使用 ms-swift 内置流程，两者不要混讲。

### 3.3 云端全量训练（已完成 · 2026-09-10）

本地实测约 **91.6 秒/优化步**，全量 19,134 条 ÷ 16 = **1,196 步约需 30.4 小时**，且三次因电源管理与显存中断；故迁移 ModelScope 云端 GPU 执行全量训练。

| 项目 | 结果 |
|---|---|
| 框架 / 精度 | ms-swift 4.5.3 + QLoRA 4bit NF4 + BF16 + Flash Attention 2 |
| 超参 | 1 epoch / lr 2e-4 / batch 1 × accum 16 / max_length 1024 / 7 类线性层 |
| 训练规模 | 19,134 条 × 1 epoch = **1,196 步** |
| 实测耗时 | 11.9 秒/步 × 1,196 ≈ **3.95 小时**（本地同规模约 30.4 小时，**加速约 7.7 倍**） |
| 训练状态 | 全程无 OOM，正常结束 |
| 产物 | LoRA 适配器 154.1 MB，托管 `Huahai123654/medical-expert-lora`（公开） |

**排障要点**：核对 ms-swift 4.5.3 源码修正 8 类参数漂移（`--train_type` → `--tuner_type`、`--tensorboard` → `--report_to`、`resume_from_checkpoint auto` 改传真实路径、`swift` CLI 缺失时回退 `python -m swift.cli.sft`）；云端 peft 0.20 的 `adapter_config.json` 含本地 0.13.2 不识别字段，只清洗配置、不动权重文件。详见 `docs/云端训练工作日志.md` 第六节。

**权重回迁与三重验证**：Hub 下载 → 配置字段清洗 → 备份 200 条快速版权重为 `final_adapter_quick200` → 替换 `outputs/lora_medical_qwen/final_adapter` → 重启 WebUI；随后 CLI 推理、Gradio 5 WebUI（7860）、API 端到端（455 字回答，严格【医学推理】→【专业解答】双段结构）全部通过。正式权重 md5 与快速版不同，且 `adapter_config.json` 保留云端 Linux 基座路径，可独立核验。

### 3.4 推理与部署工程

- **双通道加载**：① 基座+LoRA 适配器（省磁盘、灵活）② 合并后完整模型（独立部署）；
- **权重合并**（`inference/merge_lora.py`）：CPU fp16 加载 → `merge_and_unload()`
  将 `W' = W + (α/r)BA` 固化 → 保存独立模型；
- **Web 服务**（`app/app.py`）：Gradio Blocks 构建，
  多轮对话、流式逐字输出、示例问题、参数可调，
  页脚保留 AI 生成内容提示。

## 五、项目心得（讲稿素材）

- **工程取舍**：家用显卡算力有限，通过 QLoRA 三件套（4bit/梯度检查点/8bit优化器）
  把 7B 微调门槛从 A100 降到 8GB 消费级显卡；进一步以「本地验证 + 云端全量」分工，
  把 30 小时压到约 4 小时，体会到算力约束下的工程决策价值；
- **数据决定上限**：CoT 数据的"推理外显"格式直接塑造了模型的输出结构，
  印证了"微调=领域知识+推理范式注入"；
- **细节决定正确性**：Loss 屏蔽看似小改动，却决定了模型是学"提问"还是学"回答"；
- **版本治理意识**：ms-swift 4.5.3 相对 v3 的参数漂移导致多处报错，
  靠解包核对源码逐项修正，说明框架锁版本与可复现记录同样重要；
- **合规意识**：系统提示词与页脚均内置"仅供参考、以专业医师意见为准"的使用边界
  约束，这是技术之外的责任意识。
